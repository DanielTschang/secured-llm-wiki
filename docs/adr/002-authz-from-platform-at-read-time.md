# ADR-002：權限在讀取時向平台即時查詢

- 狀態：已採納
- 日期：2026-09-28

## 背景

使用者的 space 權限由平台管理，並會隨人員異動改變。知識中心可以選擇同步一份權限副本，或在每次讀取時向平台查詢。

同步副本會產生第二個權限來源，兩者不一致時，知識中心可能在使用者被移出 space 後仍讓他看到內容。RD team 也希望照舊用平台管理人員，不為知識中心多做任何事。

## 決策

1. 本系統不儲存任何權限資料。`can_read(user, labels)` 在每次讀取時計算，判斷依據為平台回傳的使用者可讀 space。
2. 平台回應以短 TTL 快取（預設 5 分鐘，可設定）。若平台提供權限變更 webhook，收到事件時主動失效對應快取。
3. **fail closed**：平台無法回應且快取已過期時，拒絕存取，不沿用舊結果。
4. 使用者身分只來自 SSO。請求內容、prompt、前端參數中的任何身分或權限宣稱一律忽略。
5. 權限判斷在程式層執行，模型永遠不參與「能不能看」的決定。

## 影響

- 人員異動、space 可見範圍變更都不需要重新處理任何知識資料，最長延遲為快取 TTL。
- 平台的可用性會影響知識中心的可用性；這是刻意的取捨，安全優先於可用性。
- 查詢服務需要能以使用者身分或受信任的服務身分查詢平台 ACL。
- 所有快取（view、語意快取、檢索結果）的 key 都必須包含 effective labels，確保權限不同的使用者不共用結果。

## 考慮過的替代方案

- **同步 AD 群組或平台 ACL 副本**：多一個權限來源，撤權延遲取決於同步頻率，且不一致時難以察覺。
- **在 ingest 時把讀者清單寫進資料**：權限變更時需要重新處理大量資料，而且讀者清單本身就是敏感資訊。
